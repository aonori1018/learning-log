# CS50 2022 Problem Set 3: Plurality 学習ノート
 
## 概要
- 課題：Week 3 / Problem Set 3「Plurality」— 相対多数決で当選者を決めるプログラムの、配布コードにある未実装の関数を完成させる
- 学べたこと：
  - 比較演算子や初期値の選び方で、コードの意図の伝わり方が変わる
  - 配列の要素を使う前に、その要素が存在する保証がどこにあるかを確認する
  - 処理の分け方を、読みやすさと計算量（Big O）の両面から比べる
## 考え方
1. 勝者を決めるため、まず全候補者の中で最多の得票数を確定させる
   - 途中の時点での最大値は全体の最大とは限らないので、確定する前に勝者は決められない
2. 確定した最多得票数と一致する候補者の名前を出力する（同票なら全員)
## つまずいたポイント
### 1. CS50 スタイルからのずれ（レビューで指摘）
- 関数呼び出しで、関数名と括弧の間にスペースを入れていた
  - 同じファイル内の他の呼び出しと書き方が揃わず、一貫性がなくなる
- 作業用の変数を、大文字1文字で命名していた
  - C の慣習では大文字の名前は定数に使うため、定数と誤解されやすい
  - 1文字では、何を保持しているか読み手に伝わらない
- 戻り値のない関数の末尾に、不要な return を書いていた
### 2. 意図が正確に伝わらない書き方（レビューで指摘）
- 大小比較で「以上」を使っていた
  - 結果は変わらないが、同じ値で無意味な上書きが起きるうえ、「より大きいときだけ更新する」という意図が表れない
- 作業用の変数の初期値を固定値にしていた
  - 今回は値が負にならないので動くが、データの値の範囲に依存した書き方になる
## 気づき
- 書き方は「動くかどうか」だけでなく、「意図が読み手に伝わるか」で選ぶ
- 配列の要素を使った初期化は、要素が最低1つあることを前提にしている。今回その前提を保証しているのは、配布コードのコマンドライン引数チェック
- 全体を見終わるまで確定しない値がある。途中の値で判断しようとすると難しくなる
- 処理を分けると手順は増えるが、定数倍の差は Big O では同じオーダー。シンプルさを優先してよい場面がある
- 比較が1回増える程度の差より、読みやすさを優先してよい。大事なのは、どちらを選んだかを説明できること
- エッジケース（有効票が0）を実際に試し、挙動が仕様と矛盾しないことを確かめる
