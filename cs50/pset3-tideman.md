# CS50 2022 Problem Set 3: Tideman 学習ノート
 
## 概要
- 課題：Week 3 / Problem Set 3「Tideman」— 順位付き投票から、ペアごとの勝敗をグラフにして当選者を決めるプログラムの、配布コードにある未実装の関数を完成させる（Runoff との選択制で、難しいほうを選んだ）
- 学べたこと：
  - 再帰の組み立て方（止まる条件と、1段ぶんの処理）
  - 2次元の真偽値配列でグラフを表し、閉路ができるかを判定する考え方
  - 講義で習ったソートを、自分で実装して使う
  - 関数が1つずつ単独でテストされることを意識した書き方
## 考え方
1. ペアの並べ替えは、講義で習ったソートの1つを自分で実装した
   - 要素の入れ替えには、一時的な変数が必要
2. ロックの判定では、配布コードの `locked` が矢印の有無を真偽で表していることに着目した。新しい矢印を足すと閉路ができるかを、既存の矢印を辿って調べる方針にした
3. 辿る処理は、最初は段数を決め打ちにした多重ループで書こうとした。各段が同じ問いの繰り返しだと気づき、再帰に切り替えた
4. 勝者は、仕様の定義どおり「矢印が1本も向いていない候補者」として判定した（最初は別の方法で判定していた）
## つまずいたポイント
### 1. 最初の関数から難しかった
- Plurality と比べて、仕様を読み込む段階から重かった
### 2. 閉路の判定を、段数固定の多重ループで書こうとした
- 何段辿れば足りるかは候補者数で変わるので、決め打ちにできない
- 内側の段ほど、外側の条件がすでに偽でも無駄にループを回していた
- ループの上限を1つ少なくしていて、最後の候補者を辿れなかった
### 3. 再帰が止まらず、スタックオーバーフローした
- 矢印があるかを確かめる前に、再帰呼び出しをしていた（論理積は左から評価されるので、順番に意味がある）
- 再帰呼び出しの引数が前に進んでおらず、同じ呼び出しを繰り返していた
### 4. 「見つからなかった」ときの終了条件が分からなかった
- 特別な条件を書こうとしていた。実際には、すべての行き先を試し終えた結果として表せた
### 5. 「完成」と思っていた関数が壊れていた（レビューで指摘）
- ペアの追加で、1つ見つけるたびに配列の全要素を上書きしていた
- ペア数を公式で決めていて、同票の場合を考えていなかった
- 勝者判定のループの上限に、候補者数ではなくペア数を使っていた
- 勝者の出力に改行がなかった
### 6. 仕様の定義とのずれ（レビューで指摘）
- 勝利の強さを「票の差」で計算していた。仕様の定義は「勝った側を支持した人数」
  - 全員が全候補者を順位付けするので、2人の票の合計は投票者数になり、並び順は同じになる。それでも仕様の定義に合わせた
### 7. スタイル（レビューで指摘）
- `for` や `if` のあとのスペースが抜けていた（関数呼び出しとは逆のルール）
- 真偽値を、さらに真と比較していた
- 中身が別の関数を1回呼ぶだけの、不要な関数を作っていた
- 文末のセミコロン抜け、行末の余分な空白
## 気づき
- 与えられたデータ構造には意図がある。それが何を表しているかを読むことが、解き方の入口になる
- 同じ問いが入れ子で繰り返されていたら、再帰の合図
- 再帰で考えるのは「いつ止まるか」と「1段ぶん何をして、残りを自分自身に任せるか」の2つだけ
- 止まる条件は、例外を弾くためだけでなく、再帰の終了の合図にもなる。これに気づくと、別に書いていたチェックが不要だと分かった
- グラフに閉路がないことが保証されているので、矢印を辿っても迷子にならず、必ず止まる
- 「見つからない」は、全部試し終えた結果として表せる（Plurality の投票処理と同じ構造）
- 動いているように見えても、途中の配列の中身を確かめないと、壊れていることに気づけない
- 仕様の定義と同じ結果になる別の計算でも、仕様の言葉どおりに合わせておくほうが安全
