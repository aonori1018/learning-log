# Missing Semester 2020 第1回：講座概要＋シェル 学習ノート

## 概要
- 範囲：本文（シェルとは、引数、PATH、パス、`ls` と権限、`mv`・`cp`・`mkdir`・`man`、ストリーム、`sudo` と sysfs）＋実践課題11問
- 学べたこと：
  - シェル・ターミナル・カーネルが、それぞれ何を担当しているか
  - コマンドラインが argv になるまでと、PATH でプログラムが探される仕組み
  - 権限をチェックするのは誰で、どういう順番で判定するか

## 学べたこと
1. シェルはカーネルの一部ではなく、普通のプログラム。ターミナル（窓）とシェル（中で動くプログラム）は別物
2. プログラム（ファイル）は1つでも、実行するたびに別のプロセスができる。プロセスごとにメモリは分かれている
3. シェルがコマンドラインを空白で分けて argv を作る。クォートと `\` はシェルへの指示で、プログラムには届かない（CS50 の `string argv[]` と同じもの）
4. 名前だけで打つと、PATH を左から順に探して、最初に見つかったものを実行する。`/` を含む名前は、その場所を直接実行する
   - `echo` は bash の組み込みコマンド。`type` で確かめられる（`which` は組み込みを見られない）
   - PATH に `.` を入れないのは PATH ハイジャックを防ぐため
5. 環境変数と「今いる場所」は、子プロセスにコピーが渡される。だから `cd` は、シェルの組み込みでないと意味がない
6. 権限をチェックするのはカーネル。プロセスの名札（UID/GID）とファイルを見比べ、所有者 → グループ → その他 の順で、**最初に当てはまった1つだけ**を使う
   - ディレクトリは名簿：`r` は一覧表示、`w` は追加・削除、`x` は通り抜け。途中のディレクトリすべてに `x` が必要
7. 0番（入力）・1番（出力）・2番（エラー）。`<`、`>`、`>>`、`|` でつなぎ替えるのも、ファイルを開くのもシェル
8. `sudo echo 3 > file` が失敗するのは、`file` を開くのが一般ユーザーのシェルだから。`echo 3 | sudo tee file` なら root の `tee` が開くので成功する

## 実践課題で分かったこと
- shebang（`#!`）を読むのはカーネル。コンパイル済みのファイル（ELF）は `x` だけで動くが、スクリプトは `r` と `x` の両方が必要（インタープリタが中身を読むため）
- `touch` の本来の目的は時刻の更新（`make` は mtime を見て判断している）
- `/tmp` のスティッキービット（`t`）
- `chmod` の記号表記（`u+x`）と数字表記（644 = `rw-r--r--`）
- `~` と `$HOME` は、プログラムに届く前にシェルが置き換える
- WSL でバッテリーの情報が見えないのは、カーネルが仮想のハードウェアしか知らないから

## つまずいたポイント
### 1. `>` のファイルを開くのは誰か
- 問題：`grep ... > file` で `file` を開くのは grep だと答えた
- 原因：リダイレクトを、コマンドが持っている機能だと思っていた
- 学び：`<` `>` `|` はシェルが処理し、つなぎ終えてからプログラムを起動する。第2回以降は `sudo` との組み合わせで正しく使えた
### 2. 権限の「名札」と「判定結果」の区別
- 問題：`ls -l` の先頭の3文字を「自分の権限」と読んだ
- 原因：自分がどの区分（所有者・グループ・その他）に当たるかを、先に決めていなかった
- 学び：先頭の3文字は所有者の権限。自分の区分を決めてから、その3文字だけを見る
### 3. argv と標準入力の区別
- 問題：パイプで流れてきたデータが argv になると考えた
- 学び：argv（注文票）と0番（ベルトコンベア）は別の通り道。0番を読むかどうかはプログラム次第

## 気づき
- 「誰が」その処理をしているか（シェル・プログラム・カーネル）を考えると、エラーの原因が分かる
- PATH ハイジャックやパストラバーサルのように、仕組みを知るとセキュリティの話につながる
- 意味の分からないコマンドをコピペすると、動かないときは直せないし、動いたときも何が起きたか分からない
