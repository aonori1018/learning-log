# Missing Semester 2020 第6回：バージョン管理（Git） 学習ノート

## 概要
- 範囲：本文（Git のデータモデル、ステージング、ブランチとマージ、リモート、`amend`・`rebase -i`・`blame`・`stash`・`.gitignore`・`bisect`）＋演習
- 学べたこと：
  - コミット・tree・blob と、それを指すブランチ（付箋）の関係
  - 手元のブランチ、手元にある GitHub の記録（`origin/〜`）、GitHub のブランチが、別々に動くこと
  - 過去のコミットを作り直す操作と、その危険

## 学べたこと
1. Git の中身は blob（ファイル）・tree（フォルダ）・commit のオブジェクト。ID は中身から計算されるので、中身が同じなら同じ ID になる
2. ブランチと HEAD は、コミットを指す付箋（リファレンス）。コミットそのものではない
3. `git add` で下書き（ステージング）に入れ、`git commit` で記録する
4. マージと fast-forward、`rebase`
5. `commit --amend` は元のコミットを直すのではなく、同じ親を持つ新しいコミットを作る。push 済みのコミットには使わない
6. `rebase -i` で過去のコミットを drop・edit できる。後ろのコミットはすべて作り直される（ID が変わる）
7. 手元の `main`、手元にある GitHub の記録 `origin/main`、GitHub の `main` は別々の付箋。リポジトリは、その中でコマンドを打ったときだけ変わる
8. `.gitignore` は、すでに追跡しているファイルには効かない（`git rm --cached` で追跡を外す）
9. `git bisect` は二分探索。16コミットなら4回で、バグが入ったコミットを特定できる

## 手を動かしたこと
- `~/dotfiles` を GitHub に公開（SSH の鍵を登録して push）
- ブランチ → プルリクエスト → マージ → 手元で `git pull`（dotfiles に README を追加）
- パスワードを入れてしまったコミットを `rebase -i` で消す練習
- 講座サイトのリポジトリを clone し、`git blame` と `git show` で、ある設定が入った理由を調べた
- `git bisect` で、16コミットの中からバグが入ったコミットを予想どおり4回で特定した

## つまずいたポイント
### 1. ブランチとコミットの言葉が混ざる
- 問題：fast-forward できる条件を、HEAD を使って説明した
- 学び：条件は「今いるブランチが指すコミットが、取り込むコミットの祖先かどうか」。付箋（ブランチ・HEAD）とコミットを分けて考える
### 2. 手元と GitHub の付箋の区別
- 問題：「push したら GitHub の main に反映される」「GitHub でマージしたら手元の main も変わる」と考えた
- 学び：push は、コマンドに書いた名前の付箋だけを動かす。GitHub でマージしても、手元は `git pull` するまで変わらない
### 3. 作り直すコミットと捨てるコミット
- 問題：`rebase -i` で drop したコミットも作り直されると考えた
- 学び：drop したコミットは作られずに消える。作り直されるのは、その後ろのコミットだけ
### 4. detached HEAD と、`checkout` での変更の持ち越し
- 過去のコミットに `checkout` すると HEAD がブランチを指さなくなる。作業中の変更は、ぶつからなければ持ち越される

## 気づき
- push・fetch・pull の前後で、「手元の付箋」「手元の記録 `origin/〜`」「GitHub の付箋」の3つがどこを指しているかを確かめる
- ブランチの感覚はまだつかみきれていないので、CS50 の課題の管理で使いながら慣れる
- 秘密を push してしまったら、履歴から消すだけでなく、パスワード自体を変える
